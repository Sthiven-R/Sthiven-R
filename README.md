<details>
<summary><b>🧠 &nbsp; How I build</b> &nbsp;—&nbsp; the engineering doctrine</summary>

<br>

- **Simple, not easy.** One articulable responsibility per module, explicit over clever. Duplication beats the wrong abstraction.
- **No happy path.** Error paths before success paths. Nothing irreversible without thinking it through first.
- **Stop patching.** Find the root cause and design the whole solution before writing code.
- **Documentation that doesn't lie.** A comment that promises unimplemented behavior is a critical bug.
- **Measure, don't guess.** Before/after on a representative workload — an opinion is not a benchmark.

</details>
